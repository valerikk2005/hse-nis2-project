# План эксперимента

## 1. Что проверяем

Исследуем создание постов в Social Network из [плана проекта](project.md).
При увеличении нагрузки сравниваем среднюю задержку, p50, p95 и p99.
Затем проверяем, влияет ли изменение ресурса найденного узкого места на задержку всего запроса.

**Baseline** - конфигурация для сравнения, где выбранному сервису доступно 1 ядро CPU.
Сервис выбираем по пробным запускам, трассам и метрикам.

| Серия | CPU-лимит выбранного сервиса |
| --- | --- |
| Baseline | 1 ядро |
| Уменьшенный ресурс | 0,5 ядра |
| Увеличенный ресурс | 2 ядра |

Во всех трёх сериях остальные настройки одинаковые.
Проверяем применение лимита и наличие свободного CPU на машине.
Если ограничение связано с другим ресурсом, меняем соответствующий ресурс и обновляем план до основных серий.

## 2. Данные и нагрузка

- **Социальный граф:** `socfb-Reed98`, пользователи и подписки создаются штатным скриптом.
- **Начальные данные:** по 10 постов на пользователя, одинаковое исходное состояние перед каждым запуском.
- **Запрос:** `POST /wrk2-api/post/compose`.
- **Содержимое:** 256 ASCII-символов, без URL, упоминаний и медиа.
- **Автор:** случайный пользователь из созданного набора.

Для основной нагрузки подготовим Lua-скрипт с фиксированным seed (начальным значением генератора случайных чисел).
Это позволит повторять последовательность запросов при сравнении конфигураций.
Штатный `compose-post.lua` используем для первого запуска, поскольку он добавляет также медиа, URL и упоминания.

## 3. Параметры запуска

| Параметр | Значение |
| --- | --- |
| Генератор | wrk2, 2 потока, 100 соединений |
| Ступени нагрузки | 10, 20, 40, 80, 160, 320, 640 запросов/с |
| Прогрев | 60 секунд на текущей интенсивности |
| Измерение | 300 секунд |
| Повторы | 3 для каждой ступени в каждой серии |
| Seed повторов | 101, 202, 303 |
| Сбор ресурсов | Раз в секунду |

Это начальные параметры.
После пробных запусков уточним диапазон, чтобы в каждой серии были низкая нагрузка, насыщение и перегрузка.
Если 640 запросов/с недостаточно, продолжим удваивать поток; если перегрузка наступает раньше, добавим меньшие ступени.
Окончательные параметры зафиксируем до основных измерений и применим ко всем сериям.

**Порядок одного запуска:**

1. Восстановить исходные данные и проверить готовность сервисов.
2. Выполнить прогрев на выбранной интенсивности.
3. Запустить измерение и сбор метрик.
4. Сохранить результаты, трассы и ошибки.
5. Перед следующим запуском снова восстановить исходное состояние.

Между повторами будем менять порядок трёх конфигураций.
Для соответствующих повторов используем одинаковые seed.

## 4. Метрики

| Метрика | Что показывает и как собирается |
| --- | --- |
| Средняя задержка, p50, p95, p99 | Время запроса в мс, статистика клиента wrk2 |
| Заданный и фактический поток | Запросов/с, параметры и вывод генератора |
| Успешные ответы | Запросов/с, счётчики ответов без ошибок |
| Ошибки и таймауты | Количество и доля от отправленных запросов, wrk2 и логи frontend |
| CPU и память | Занятые ядра и МиБ по каждому сервису, Docker/cgroup |
| CPU throttling | Время ограничения CPU, cgroup |
| Длина очереди | Число ожидающих запросов, счётчик приложения или добавленная инструментация |
| Время вызовов | Длительность RPC в мс, Jaeger |

Если счётчика очереди нет, добавим его для выбранного сервиса до основных серий.
Число активных запросов включает и ожидание, и выполнение, поэтому не заменяет длину очереди.
Настройка sampling (доли записываемых трасс) Jaeger будет одинаковой во всех сериях.

**Признаки насыщения:** рост очередей, ошибки и отставание успешных ответов от заданного потока более чем на 5%.
Дополнительно проверим, что сам генератор способен выдерживать нужную интенсивность.

## 5. Проверка корректности

Перед тестами создадим пост с уникальным текстом и найдём его в ленте автора.
Для домашней ленты используем пользователя с заранее известной подпиской на автора.
Проверяем содержимое ответа: HTTP 200 сам по себе не подтверждает правильность работы.

## 6. Обработка результатов

Для каждого запуска сохраняем параметры, вывод wrk2, метрики, трассы и ошибки.
Построим графики задержки, пропускной способности, ошибок, ресурсов и очередей в зависимости от нагрузки.
Сравним рост средней задержки, p95 и p99 относительно низкой нагрузки.
По трём повторам покажем медиану и разброс результатов.
P99 отдельных запусков не будем усреднять как общий квантиль.
Таймауты учитываем отдельно: при перегрузке статистика завершённых ответов не описывает все запросы.

**Поиск причины:** по трассам отделяем собственную работу сервиса от ожидания его зависимостей и сопоставляем это с ресурсами и очередями.
После изменения CPU сравниваем p99 и начало насыщения на тех же ступенях нагрузки.
Затем повторяем baseline на низкой и близкой к насыщению нагрузке, чтобы проверить возврат результата.
Если изменение не превышает разброс между повторами, причинная связь пока не подтверждена.

**Материалы:** исходные данные - `results/raw/`, обработанные таблицы - `results/processed/`, графики - `results/figures/`.
Команды запуска и скрипт обработки сохраним в репозитории.
Здесь описан план; фактические результаты добавим после запусков.
